# AudioMancer Project Export Service

## 1. Purpose

`project_export_service.py` provides user-facing export projections for ready
project artifacts on the Home / Project page. It turns runtime cleanup,
chunking, translation, character, and Speech Blocks artifacts into TXT or
Markdown documents, and packages generated voice/audiobook assets into ZIP
archives without changing the active project workspace.

## 2. Responsibilities

- Report readiness for the Home export rows: Cleaned Text, Text Chunks,
  AI Translation, Characters, Narator Voice, Character Voices, Speech Blocks,
  and Audio Assembly.
- Require both a completed manifest operation and a usable root-level artifact
  for text exports; allow voice and Audio Assembly ZIP exports when at least
  one generated sample or output file exists.
- Render UTF-8 TXT and Markdown content with a common project/source header.
- Create ZIP archives for available Narator Voice samples, Character Voices
  samples, and Audio Assembly outputs.
- Suppress internal ids and JSON metadata from exported chunk, translation, and
  Speech Blocks body text.
- Provide helper behavior for default file names, extensions, and
  inside-project save-path rejection.

The service does not open dialogs, update `project.json`, or register exported
deliverables as runtime artifacts. It writes ZIP archive files only when the
Home controller explicitly calls `create_archive_export`.

## 3. Implementation Overview

The service exposes five main functions:

- `build_export_states(project_root, manifest)` returns ordered dictionaries
  consumed by the Home page export panel.
- `default_export_file_name(manifest, export_kind, export_format)` builds a
  safe default deliverable name.
- `is_path_inside_project(project_root, export_path)` lets the controller
  reject paths equal to or below the active project root.
- `render_export(project_root, manifest, export_kind, export_format)` builds a
  normalized `ExportDocument` and renders it as TXT or Markdown.
- `create_archive_export(project_root, manifest, export_kind, export_path)`
  writes ZIP exports for generated voice samples or Audio Assembly files.

Each export kind has a dedicated document builder that reads the existing
operation report, operation state, and output artifact through established
service loaders. The shared `ExportDocument` model keeps the header fields,
operation parameters, and body sections format-neutral so a later PDF renderer
can reuse the same projection layer.

## 4. Dependencies

Internal dependencies:

- `audiomancer.config` for root-level artifact file names.
- Cleanup, chunking, translation, character-discovery, and Speech Blocks
  service loaders.
- Narrator-definition, Character Voices, and Audio Assembly service loaders.
- `token_usage_service` for normalized provider token counters.
- Home page and Home controller UI code consume the service output.

External dependencies:

- Python standard-library `pathlib`, `datetime`, `dataclasses`, `re`, and
  `zipfile`.

## 5. Inputs And Outputs

Inputs:

- Active project root path.
- Active `project.json` manifest dictionary.
- Root-level runtime artifacts such as `clean_text.txt`,
  `chunks_text.json`, `translated_text.json`, `characters_profile.json`, and
  `speech_blocks.json`.
- Optional operation reports and state files used for export parameters.
- Generated narrator/character voice sample WAV files and Audio Assembly WAV
  outputs when ZIP archive exports are requested.

Outputs:

- Readiness dictionaries for UI rows.
- Rendered TXT or Markdown strings for the selected export.
- ZIP archives containing available generated audio files plus companion text
  metadata or an Audio Assembly manifest.

## 6. Data Contracts

Readiness is based on:

- `manifest["operations"][operation_kind]["status"] == "completed"`.
- Required artifact file exists at the active project root.
- Required artifact contains usable text or records.

ZIP readiness is more permissive for partial progress: Narator Voice and
Character Voices become available when at least one profile/target has both a
sample WAV and sample metadata, and Audio Assembly becomes available when at
least one generated output record still points to an existing WAV file.

Every rendered export starts with:

- Project display name.
- Original source filename from `manifest.source_document.original_name`.
- Original source extension derived from that filename.
- Export type.
- UTC export timestamp.
- Operation parameters and summary fields.
- AI operation parameter fields from the operation-local transaction log when
  the exported artifact was generated by an AI workflow, including profile id,
  backend kind, base URL, model, temperature, and token-limit request
  parameters. Prompt bodies and API-key-like values are not exported.
- Speech Blocks source chunk count is taken from the Speech Blocks report when
  available; otherwise it is derived from `translated_text.json` for translated
  sources or from `chunks_text.json` for canonical chunk sources, not from
  operation-state metadata.

Body content is projected for delivery, not debugging. Text Chunks, AI
Translation, and Speech Blocks bodies include only readable text/speaker data,
not internal ids, JSON keys, or workflow metadata. Markdown character exports
render each character as its own subsection with a visible attribute table so
extracted traits, `Gender Hint`, `Age Hint`, and voice-definition fields remain
scannable.
Speech Blocks exports use the shared canonical book order helper, so blocks are
rendered by source chunk order and then by each chunk's local `sequence_index`.
Each Speech Block body renders the speaker display name on its own line and the
spoken text on the following line; Markdown exports use hard line breaks inside
each block so previewers preserve that two-line layout.

Narator Voice ZIP exports include one WAV and one companion TXT file per
sampled narrator profile. Character Voices ZIP exports do the same for sampled
character targets. Each companion TXT contains the voice definition prompt and
the preview text used for the sample. Audio Assembly ZIP exports include every
available generated WAV plus `audio_assembly_manifest.txt`, which records the
composition settings, exported file list, duration, size, and totals.

## 7. Workflow Integration

The Main Window refreshes export readiness whenever project state is shown. The
Home page displays Workflow Progress on the left as one read-only row box per
operation stage after source selection and a compact `Exports` group on the right. Export controls are placed on
the same vertical row as the workflow stage that produces that deliverable, with
only format selectors and export buttons visible. It emits
`export_requested(export_kind, export_format)` for enabled rows. The Home
controller opens `QFileDialog.getSaveFileName`, forces the selected extension,
rejects paths inside the active project root, then either renders and writes
UTF-8 content or delegates ZIP creation to the archive writer.

## 8. Usage

Typical service usage:

```python
states = project_export_service.build_export_states(project_root, manifest)
content = project_export_service.render_export(
    project_root,
    manifest,
    project_export_service.EXPORT_KIND_TEXT_CHUNKS,
    project_export_service.EXPORT_FORMAT_MARKDOWN,
)
```

Archive export usage:

```python
project_export_service.create_archive_export(
    project_root,
    manifest,
    project_export_service.EXPORT_KIND_AUDIO_ASSEMBLY,
    export_path,
)
```

The UI controller owns file-system writes:

```python
export_path.write_text(content, encoding="utf-8")
```

## 10. Limitations And Future Work

- PDF export is intentionally deferred.
- Text exports support TXT and Markdown. Voice and Audio Assembly exports
  support ZIP archives only.
- Exported files are external deliverables and are not tracked in
  `project.json`.
- Future format renderers should reuse `ExportDocument` rather than rereading
  runtime artifacts directly.
