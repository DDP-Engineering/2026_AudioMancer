## Design

Components touched: AI Translation only. The shared `ai_budget_service`
helper is deliberately left alone - AI chunking returns a handful of
integer descriptors regardless of how much text it was sent, so capping
its input by its output limit would shrink it for no reason. Translation
is the only operation whose reply is as long as its request, so the cap
belongs to translation.

Interface change (REQ-FUNC-6c7c71d9): `_build_budget_metadata` keeps
calling the shared helper, then lowers `text_budget_tokens` to
`max_output_tokens / DEFAULT_AI_TRANSLATION_OUTPUT_EXPANSION_FACTOR`
whenever that is the smaller number. The factor is a new config constant
set to 1.3, covering the length a translation gains over its source plus
JSON escaping. No signature changes and no new call sites.

Interface change (REQ-FUNC-cfa5468c): after the cap, the workflow minimum
is re-checked. The shared helper already refuses a tiny budget, but its
message blames the context window; a budget that failed the cap needs a
message naming the maximum output tokens instead, because that is the
setting the operator has to raise.

Data and storage: none. `budget_metadata` is persisted inside
`translated_text.json`, but only as integer fields that already exist -
the strict document contract validates it as an object and does not
enumerate its keys, so a changed value needs no migration.

Rejected alternative: capping inside `ai_budget_service` behind a new
optional parameter. One helper would then carry a rule that is true for
one caller and false for the other, and every future caller would have to
decide which it is. A translation-local cap keeps the rule next to the
reason for it.

Test seams: `_build_budget_metadata` is called directly by the existing
service tests, so both requirements attach there - REQ-FUNC-6c7c71d9 on
the returned `text_budget_tokens` for a wide-window low-output profile,
and REQ-FUNC-cfa5468c on the `ValueError` message for a profile whose
output limit cannot fund the workflow minimum.

Files expected to change: `config.py`, `ai_translation_service.py`, and
`test_ai_translation_service.py`.

Note for build: the existing
`test_translation_budget_reserves_output_and_rejects_insufficient_input`
compares two profiles that both sit in the output-capped regime once this
lands, where a larger output limit now yields a larger text budget. Its
assertion has to move to two profiles in the reservation-dominated regime
to keep testing what it was written to test.

## Log

- 2026-08-17 frame: AI translation sizes each request from the profile context window but never caps the source text by how much text the model is allowed to emit, and translation is the one operation whose reply is as long as its request, so a profile whose max output tokens are small relative to its context window is sent more text than it can ever translate back.
- 2026-08-17 frame: measured on the shipped defaults - a 16K window with 8192 max output tokens sends 6288 source tokens against an 8192 reply allowance and just fits, while a 32K window with the same 8192 sends 19661 source tokens against the same 8192 allowance and truncates every chunk; widening the context window makes the defect worse rather than better.
- 2026-08-17 frame: scope is the translation budget only - cap the source-text budget by the reply the profile can produce, and refuse the run with an actionable message when that cap leaves too little room.
- 2026-08-17 frame: out of scope - the shared `ai_budget_service` helper (AI chunking legitimately wants a text budget far larger than its tiny descriptor reply, so a cap there would wrongly shrink it), the AI chunking and Cleanup budgets, the prompt templates, the retry count, and the provider truncation error itself.
- 2026-08-17 frame: path is full - no existing requirement states that a translation request must fit its own reply (`REQ-FUNC-21601fff` covers only the shared helper's reservation arithmetic), and the change alters request sizing and adds an operator-facing refusal, so it needs its own requirement.
- 2026-08-17 frame: work stays on master at the operator's instruction with no commit and no push, and validation runs targeted tests only.
