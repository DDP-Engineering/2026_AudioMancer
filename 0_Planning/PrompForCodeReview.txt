You are a senior software engineer performing a deep implementation review of
the AudioMancer codebase.

Your goal is to analyze the actual software implementation and generate a
practical engineering report focused on bugs, maintainability risks, duplicate
code, dead code, inconsistent patterns, unnecessary complexity, missing tests,
and stale documentation.

Do not make code changes yet. First inspect the repository thoroughly and base
every finding on repository evidence.

Primary implementation scope:

- `04_Software/AudioMancer/`
- `04_Software/AudioMancer/src/audiomancer/`
- `04_Software/AudioMancer/tests/`
- `04_Software/AudioMancer/prompts/`
- `04_Software/AudioMancer/settings.json`
- `04_Software/AudioMancer/pyproject.toml`

Important project context:

- AudioMancer is an offline-first Python 3.12 desktop audiobook production
  application.
- The UI is implemented with PySide6.
- The project uses `uv` for environment and dependency management.
- The application stores project state and workflow artifacts as deterministic
  local files.
- The implementation is organized around service modules, page widgets, UI
  controllers, prompt templates, and focused pytest coverage.
- Long-running workflows use a Qt thread/controller path with cooperative
  cancellation and progress reporting.
- AI workflows use OpenAI-compatible provider settings and local prompt
  templates.
- TTS/audio generation integrates with a VoiceWeaver-compatible runtime.
- Current generated audio outputs are WAV-based; MP3 encoding, normalization,
  cover art, and chapter metadata are deferred unless the implementation shows
  otherwise.
- Operator-facing UI text is expected to remain language-complete through the
  runtime UI translation mechanism.
- Repository style and validation rules are defined in `AGENTS.md` and
  `01_Documentation/Code_Style.md`.

Review the codebase for:

1. Possible bugs
   - Incorrect logic
   - Edge cases not handled
   - Race conditions, threading issues, or cancellation gaps
   - Qt state-management problems
   - Project manifest, artifact, or resume-state inconsistencies
   - Reset/rerun behavior that deletes too much or preserves stale downstream
     data
   - Error handling gaps
   - Unsafe file, path, archive, shell, HTTP, or JSON handling
   - Data validation problems
   - Incorrect assumptions about APIs, files, dates, users, language settings,
     VoiceWeaver endpoints, or local environment

2. Duplicate or redundant code
   - Repeated workflow-stage logic
   - Similar controller/page patterns implemented multiple times
   - Duplicate reset, confirmation, manifest, artifact, or validation logic
   - Duplicate constants, schemas, prompt handling, settings handling,
     translation keys, URL handling, or provider/runtime clients
   - Parallel implementations that may drift over time

3. Dead or unused code
   - Unused files
   - Unused functions/classes/helpers
   - Unused imports, exports, constants, styles, routes, scripts, assets,
     prompts, settings fields, or dependencies
   - Commented-out legacy code
   - Compatibility paths that appear unreachable or obsolete
   - Code paths made stale by the current v2 artifact and stable-ID behavior

4. Architecture and maintainability
   - Overly complex modules
   - Poor separation between services, controllers, widgets, and persistence
   - UI code doing service or persistence work directly
   - Services with hidden global state or broad side effects
   - Tight coupling between workflow stages
   - Inconsistent naming or patterns
   - Files that are too large or doing too much
   - Areas where the implementation fights PySide6, pytest-qt, or standard
     Python patterns instead of using them idiomatically

5. Testing gaps
   - Important behavior with no tests
   - Fragile tests
   - Missing regression tests for workflow invalidation, resume behavior,
     project reopening, localization, cancellation, and artifact contracts
   - Areas where a small focused service or controller test would reduce risk
   - Tests whose assertions no longer match the actual intended behavior

6. Performance and reliability
   - UI freezes or long work on the Qt UI thread
   - Repeated file reads/writes that could corrupt state or slow workflows
   - Inefficient loops over large books, chunks, speech blocks, or audio blocks
   - Missing loading/error/empty states
   - Resource leaks, unclosed files, orphaned workers, or playback lifecycle
     problems
   - Poor cache invalidation or stale runtime-discovery state
   - Packaging or dependency risks visible from `pyproject.toml`, `uv.lock`,
     or packaging scripts

7. Security and safety
   - Unsafe user input handling
   - Secrets committed or exported
   - API-key-like values written to exported reports or archives
   - Insecure provider or VoiceWeaver API calls
   - Unsafe file, shell, archive, or network operations
   - Path traversal, symlink, overwrite, or project-root escape risks
   - Dependency risks visible from lockfiles or package metadata

8. Documentation consistency
   - README, software documentation, planning notes, and HowToTest content that
     no longer matches the implementation
   - Documents that describe planned behavior as implemented behavior
   - Missing component documentation for implemented services
   - Validation instructions that are stale or incomplete

Use repository evidence. Reference specific files and line numbers where
possible.

Generate a report with this structure:

# Implementation Review Report

## Executive Summary

Briefly summarize the overall health of the codebase, the most important
risks, and the highest-value fixes.

## High Priority Findings

For each finding include:

- Title
- Severity: Critical / High / Medium / Low
- File(s) and line(s)
- What is wrong
- Why it matters
- Recommended fix
- Suggested test coverage, if relevant

## Medium Priority Findings

Use the same format as above.

## Low Priority Findings / Cleanup

Use the same format as above, but keep it concise.

## Duplicate Code and Duplicate Implementations

List repeated logic, similar modules, duplicated UI patterns, duplicated
runtime/provider calls, duplicated schemas/types, duplicated translation keys,
or parallel implementations. Explain what should be consolidated.

## Dead Code / Unused Code

List likely-unused files, functions, exports, imports, dependencies, prompts,
settings fields, translation entries, styles, assets, or scripts. Clearly mark
anything that requires confirmation before removal.

## Missing or Weak Tests

List the most important tests to add first, ordered by risk reduction.

## Architecture and Maintainability Notes

Describe broader design issues, inconsistent patterns, or areas that may become
hard to maintain.

## Documentation Consistency Notes

List documentation that appears stale, incomplete, or inconsistent with the
implementation.

## Quick Wins

List small changes that are likely safe and high-value.

## Suggested Refactor Plan

Give a staged plan:

1. Safe cleanup
2. Bug fixes
3. Consolidation/refactoring
4. Test hardening
5. Documentation synchronization

## Open Questions

List any assumptions or things that need clarification before making changes.

Important instructions:

- Be specific and evidence-based.
- Do not invent issues without code evidence.
- If something is only a suspicion, label it as "Needs confirmation."
- Prefer actionable recommendations over vague advice.
- Do not recommend broad rewrites unless the code evidence clearly justifies
  them.
- Preserve public interfaces unless a change is explicitly justified.
- Treat UI translation completeness as part of any operator-facing UI review.
- Treat project artifact preservation and reset behavior as high-risk because
  unnecessary deletion can waste operator time.
- Treat secrets and operator-local runtime settings as high-risk when reviewing
  export, snapshot, logging, and packaging paths.
- Do not make changes unless I explicitly ask you to after the report.
